# Phase 1: external datastore, KMS keys, enforced TTL

This phase closes the IA-5 / SC-12 row and the datastore row of the evidence-gap
table from the practicum report.

| Practicum build | Phase 1 build |
|---|---|
| Bundled SQLite on a 1Gi EBS volume with `reclaimPolicy: Delete` | RDS PostgreSQL 16.13, encrypted, no local state |
| Disk-resident self-signed root CA (`keys.json`) | Keys created and held in AWS KMS |
| ~4h SVID TTL observed from one certificate | TTL set in configuration to 1h |
| Images pulled from public registries | Images mirrored to ECR, no egress |
| Trust domain `example.org` | Trust domain `spire-rmf.lab` |

Chart: `spiffe/spire` 0.30.3 (SPIRE 1.15.3). CRDs: `spiffe/spire-crds` 0.6.1.

## What was built

Terraform adds an RDS PostgreSQL instance in the private subnets, reachable only
from the cluster security group. The database password is generated by Terraform
and written to Secrets Manager. It is never printed as an output or committed.

An IAM role for the SPIRE server is bound to its Kubernetes service account
through an EKS Pod Identity association. The role allows the KMS actions the
`aws_kms` key manager plugin needs. Pod Identity was chosen over IRSA because it
does not require an OIDC provider, which keeps the Private Only story simpler.

## Order of operations

1. `terraform apply` for `rds.tf` and `kms.tf`. RDS takes 5-10 minutes.
2. Create the namespace and the datastore secret.
3. Mirror images to ECR (see `phase-1-images.md`).
4. `helm install` with `helm/phase-1/spire-values.yaml`.
5. Capture evidence while the cluster is running.

### Namespace and secret

```bash
cd terraform
SECRET_ARN=$(terraform output -raw spire_datastore_secret_arn)
DB_PASS=$(aws secretsmanager get-secret-value --secret-id "$SECRET_ARN" \
  --query SecretString --output text \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["password"])')

kubectl create namespace spire-server
kubectl -n spire-server create secret generic spire-datastore \
  --from-literal=password="$DB_PASS"
```

The chart reads the password from this secret through
`dataStore.sql.externalSecret`. The password does not appear in the values file
or in the Helm command line.

### Install

```bash
helm install spire-crds spiffe/spire-crds -n spire-server --version 0.6.1
helm install spire spiffe/spire -n spire-server \
  --version 0.30.3 --values helm/phase-1/spire-values.yaml
```

## Results

The server log confirms the datastore:

```
level=info msg="Opening SQL database" db_type=postgres
level=info msg="Connected to SQL database" type=postgres version=16.13
```

And the key manager:

```
level=info msg="Configured plugin" plugin_name=aws_kms plugin_type=KeyManager
level=info msg="X509 CA prepared" self_signed=true slot=A
```

KMS holds two keys after startup:

```
alias/SPIRE_SERVER/spire-rmf_lab/spire-cluster/x509-CA-A
alias/SPIRE_SERVER/spire-rmf_lab/spire-cluster/JWT-Signer-A
```

Both agents attested with `k8s_psat`:

```
msg="Agent attestation request completed"
  agent_id="spiffe://spire-rmf.lab/spire/agent/k8s_psat/spire-cluster/..."
  method=AttestAgent node_attestor_type=k8s_psat
```

## Why the KMS result matters for SC-12

KMS has no API that exports private key material. SPIRE calls `kms:Sign` when it
needs a signature, and the key stays in KMS. This is a different claim from the
practicum build, where the signing key was a file on an EBS volume that anyone
with access to the node or the volume snapshot could read.

The pod has no persistent volume at all. With the datastore in RDS and the keys
in KMS, there is nothing left for the server to write to disk, so
`persistence.type` is set to `emptyDir`. The practicum build patched gp2 in as
the default StorageClass, which left `reclaimPolicy: Delete` holding the only
copy of the identity database.

## Why the TTL result matters for IA-5

The chart ships with `defaultX509SvidTTL: 4h`. The practicum reported a roughly
4 hour validity window as evidence of short-lived credentials, but that was the
chart default, not a configured policy. Phase 1 sets it to 1h, so the value in
the rendered config is visibly a decision. The evidence is the config and an
issued SVID together. Either one alone is weak.

## Problems hit during the build

**The jump host cannot run the install.** Helm and the chart repository need
internet access. Everything runs from the workstation, with kubectl and Helm
reaching the private API endpoint through an SSM port forward. That session
times out, and any long Helm command will fail with a TLS handshake timeout when
it does. Check `kubectl get nodes` before starting anything long.

**Images do not come from one registry.** See `phase-1-images.md`. This took six
separate value overrides to resolve and was the largest single time cost of the
phase.

**KMS key management turned out to be the hardest part of the phase.** Four
separate failures, written up in full in `phase-1-kms.md`: the plugin's default
key policy can orphan keys permanently across a rebuild, the lockout safety
check requires `kms:PutKeyPolicy`, tag-based key discovery needs its own VPC
endpoint for the Resource Groups Tagging API, and CoreDNS caching hid the fix
for that. Two keys from the first build are permanently unmanageable as a
result. That document is the most substantial finding in this phase.

**The KMS plugin needs a key identifier.** Setting `keyIdentifierFile.enabled`
to false is not enough on its own. The plugin needs either a file or a static
value so it can recognise its own keys after a restart. The value form is used
here because it needs no volume:

```yaml
keyIdentifierValue:
  enabled: true
  identifier: spire-cluster
```

Without it the server crashes with
`configuration requires a key identifier file or a key identifier value`.

**Helm reports the release as failed even when the install works.** The chart
creates three default `ClusterSPIFFEID` resources in the same pass as the
server. The webhook that validates them runs inside the server pod, which is not
serving yet, so the apply fails with `no endpoints available for service
"spire-controller-manager-webhook"`. The pods still come up. Phase 2 replaces
those default identities with purpose-built ones, which removes the problem.

**The server image is distroless.** There is no shell, so `kubectl exec ... ls`
does not work. Evidence has to come from the Kubernetes API and the AWS APIs
instead of from inside the container. That is a point in favour of the image,
not against it, but it changes how evidence is collected. An assessor used to
logging into hosts will need a different workflow.

## Deviations to state in the paper

- **RDS is single-AZ by default.** `rds_multi_az` defaults to false to keep cost
  down. The datastore is external, which removes the SQLite single-writer
  ceiling, but a single-AZ instance is not high availability. Either set the
  variable to true for the evidence run or describe the datastore as external
  and single-AZ. Do not claim HA from this.
- **One SPIRE server replica.** An external datastore makes replicas possible.
  Running them is a separate claim and needs separate evidence.
- **The KMS IAM policy uses `Resource: "*"`.** `kms:CreateKey` does not support
  resource-level constraints. The key operation statement should be narrowed to
  the created key ARNs after the first run, and that narrowing is itself AC-6
  evidence.
- **This is not FIPS.** KMS uses validated hardware, but SPIRE's own TLS stack
  is a separate question. That is Phase 5. Do not let the KMS result blur into
  an SC-13 claim.
- **Alias-based key discovery is deprecated.** The server logs a warning
  recommending `enable_tag_based_key_discovery`. Worth noting as a known
  follow-up.
