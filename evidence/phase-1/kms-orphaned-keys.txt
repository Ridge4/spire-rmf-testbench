Attempting to disable these keys from the AWS console, as the account root,
returned:

  AccessDeniedException - User: arn:aws:iam::401352756244:root is not
  authorized to perform: kms:DisableKey on resource:
  arn:aws:kms:us-east-1:401352756244:key/928e84df-9901-4438-9fcf-89e4169b67cf
  because no resource-based policy allows the kms:DisableKey action

This is the part worth stating carefully. AWS's usual guarantee is that the
account root retains control of its own keys. That guarantee holds only if the
key policy grants it. The aws_kms plugin's default policy gives root
kms:Describe*, kms:List* and kms:Get* and nothing more, so root can see these
keys and cannot act on them.

Control implication, CP-10. Rebuilding from infrastructure as code is supposed
to be a recovery capability. With the plugin's default key policy, the rebuild
destroys the trust anchor rather than restoring it, and the destruction is
irreversible. The mitigation is an explicit key policy granting the account
root full administrative access, as in helm/spire-values.yaml from Phase 1
onward.
